# مناقيش — نظام مركزي لمنشورات فيسبوك المحفوظة

نظام ويب متكامل يجمع كل المنشورات التي يحفظها الفريق عبر إضافة **Facebook Post Saver**
في مكان واحد، مع إدارة أدوار وصلاحيات، ونظام ترجمات متعدد اللغات، وتصدير منفصل لكل لغة.

> **البنية الحالية:** الموقع **تطبيق ثابت** يعمل بالكامل في المتصفح ويتصل بـ Supabase
> مباشرة (RLS + محفزات قاعدة البيانات تفرض كل الصلاحيات)، لذا يُستضاف مجانًا على
> **GitHub Pages** أو **Firebase Hosting** — الخطوات الكاملة في
> [HOSTING.md](./HOSTING.md). [DEPLOY.md](./DEPLOY.md) يوثّق بنية سيرفر Next.js
> القديمة على Vercel (للمرجعية التاريخية).

---

## ما الذي يفعله النظام

| القدرة | التفصيل |
|---|---|
| تجميع تلقائي | كل منشور يحفظه أي مستخدم يصل إلى قاعدة البيانات لحظة حفظه، ويظهر عند المدير فورًا |
| أربعة أدوار | مدير · محرر · مستخدم (جامع منشورات) · مترجم |
| تحكم يدوي بالدخول | كل حساب جديد يبدأ **بانتظار التفعيل**، والمدير وحده يفعّله ويحدد دوره |
| ترجمات متعددة اللغات | زر «إضافة لغة» لكل منشور؛ كل لغة ترجمة مستقلة، واللغات تُضاف تدريجيًا |
| تصدير حسب اللغة | كل لغة تُصدَّر منفصلة: Excel · CSV · JSON · Markdown · WordPress WXR |
| سلة المهملات | الحذف من النظام نقل مؤقت؛ الزبون «🗑 سلة المهملات» يعرض المحذوفات ويعيدها بزر «♻» فرديًا أو جماعيًا |
| تحديد وإجراءات جماعية | تحديد عدة منشورات من الجدول: تغيير الحالة، الحذف، الاستعادة — وتغيير صاحب البوست (المدير) |
| تغيير صاحب البوست | المدير وحده يصحّح «حساب فيسبوك» المنسوب إليه المنشور (عمود الحساب ✏️)؛ أما **العضو الذي حفظ المنشور فثابت** ولا يمكن تغييره لأحد |
| إعدادات المظهر | المدير يضبط الألوان والخطوط وأحجامها وعرض/ارتفاع خلايا الجدول من تبويب «الإعدادات»، وتُطبَّق على كل الموقع |
| كلمة مرور للأعضاء | المدير يعيّن كلمة مرور لأي عضو (مثل من دخل بحساب Google) فيصبح «تبديل الحساب» ممكنًا |
| سجل نشاط | المدير يرى من عدّل ماذا ومتى |

## الأدوار بالتفصيل

| الدور | يرى | يعدّل | الأعضاء | الصلاحيات |
|---|---|---|---|---|
| **مدير** | كل المنشورات | كل شيء | يرى ويدير الجميع | يتحكم في كل شيء |
| **محرر** | كل المنشورات | كل المحتوى | **لا يرى أحدًا** | لا يتحكم في الصلاحيات |
| **مستخدم (collector)** | منشوراته فقط | منشوراته فقط | لا يرى أحدًا | يحمّل الإضافة ويحفظ |
| **مترجم** | كل المنشورات | الترجمات | **لا يرى أحدًا** | لا يتحكم في الصلاحيات |

قاعدة «المحرر والمترجم لا يريان الأعضاء» مطبَّقة في ثلاث طبقات:
منع في الواجهة، منع في مسارات الـ API، ثم منع في سياسات RLS بقاعدة البيانات.

## التشغيل محليًا

```bash
# 1) انسخ ملف الإعدادات واملأ القيم
cp .env.example .env.local

# 2) ثبّت الحزم (المستودع يحمل pnpm-lock.yaml؛ npm يعمل أيضًا)
pnpm install

# 3) شغّل
pnpm dev      # http://localhost:3000
```

للتحقق قبل النشر:

```bash
pnpm typecheck    # فحص الأنواع
pnpm build        # بناء الإنتاج
```

> **مهم:** تعمل ميزات التحقق فقط عند تشغيل قاعدة البيانات والترحيل. راجع
> [DEPLOY.md](./DEPLOY.md) للخطوات الكاملة.

## كيف تتصل الإضافة بالنظام

الإضافة صُممت لتتصل بـ Supabase **مباشرة**، لذلك لا تحتاج إلى تعديل منطقها:

```
مستخدم يحفظ منشورًا
   └─► POST /rest/v1/posts?on_conflict=user_id,post_key   (من خدمة الإضافة)
          └─► user_id يُؤخذ تلقائيًا من رمز الدخول (DEFAULT auth.uid())
                 └─► RLS يشترط أن يكون user_id = صاحب الرمز

مستخدم يسجّل الدخول من الإضافة
   └─► يفتح {siteUrl}/connect
          └─► Google → Supabase → الصفحة ترسل الجلسة للإضافة عبر postMessage
```

**التغيير المطلوب في الإضافة:** ثلاثة ملفات في مجلد `extension-patch`
(`manaqish-config.js` لتغيير العنوان، `manifest.json` للسماح بالنطاق الجديد،
و `manaqish-bridge.js` المُشدَّد بفحص النطاق). بقية ملفات الإضافة — الجدول والحفظ
والتصدير — لا تُلمس.

## ملاحظات أمنية

1. **المفتاح العام داخل الإضافة سيصبح معروفًا** لأي شخص يفحص الإضافة. هذا طبيعي في
   Supabase، ولذلك كل جدول محمي بـ RLS، ودور `anon` لا يملك أي صلاحية على البيانات.
2. **الإضافة لا تستطيع حذف منشورات غيرها.** سياسة الحذف تشترط `user_id = auth.uid()`،
   لأن طلب الحذف من الإضافة يُفلتر على `post_key` فقط دون أي شرط على المستخدم.
3. **مفتاح الخدمة السري** (`SUPABASE_SERVICE_ROLE_KEY`) يبقى في Vercel فقط، ولا يدخل
   الإضافة أو المتصفح أبدًا.
4. **الحسابات الجديدة معطّلة افتراضيًا** (`pending`)، فلا يستطيع أي حساب Google عشوائي
   قراءة أو كتابة أي شيء قبل تفعيل المدير له.

## صيانة المخطط مستقبلًا

كل تعديل على قاعدة البيانات يُضاف كملف جديد في `supabase/migrations/` بالترقيم التالي
(`0002_...sql`، `0003_...sql`)، ولا يُعدَّل الملف الأول بعد تنفيذه على قاعدة حقيقية.

> **تنبيه مهم:** أسماء الأعمدة المتعلقة بالإضافة (`post_key`، `post_date`،
> `markdown_text`، `image_urls`، …) هي **عقد ثابت** مع إضافة Facebook Post Saver.
> تغيير أي منها يكسر المزامنة بصمت.
